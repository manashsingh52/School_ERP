# Deploying Bastaa (Google Cloud, lean mode)

What runs where (docs/10 §0, lean mode — about $25–45/month for staging):

| Piece | Service | Notes |
|---|---|---|
| API + background jobs | Cloud Run `schoolos-api` | `RUN_WORKERS=true`; Chromium for PDFs; 2 GiB. Staging scales to zero (scheduled jobs then run only while awake); production keeps 1 instance with CPU always on |
| Web (Next.js) | Cloud Run `schoolos-web` | standalone server; school subdomains and the `admin.` console |
| Migrations | Cloud Run job `schoolos-migrate` | `prisma migrate deploy` + RLS policies, as the owner role, before each deploy |
| Database | Cloud SQL Postgres 17 | staging `db-f1-micro`; production `db-custom-1-3840`, PITR, 30 backups. Reached over Cloud Run's built-in Cloud SQL connector (no public IP allow-list) |
| Files | Cloud Storage | private bucket (signed links), public bucket (logos) |
| Secrets | Secret Manager | generated by `bootstrap.sh`, never printed or committed |
| Edge | Cloudflare (DNS, TLS, WAF) + Worker `infra/cloudflare/worker.js` | routes `*.<domain>` → web, `api.<domain>` → API; adds the edge secret, without which the `run.app` URLs answer 404 |

Images are built by **Cloud Build** — no Docker needed on your Mac. CI also builds them on every push, so a broken Dockerfile is caught before deploying.

## First time (≈ 1 hour, most of it waiting for Cloud SQL)

Prerequisites: a Google Cloud project with billing (the $300 credit works), `gcloud` (installed), a domain on Cloudflare.

```bash
gcloud auth login
gcloud auth application-default login

# 1. Project: APIs, registry, Cloud SQL, buckets, service accounts, secrets, GitHub deploy access
ENV=staging PROJECT_ID=<your-project> DOMAIN=<your-domain> GITHUB_REPO=<owner/repo> ./infra/gcp/bootstrap.sh

# 2. Database roles (owner / app / platform), once
ENV=staging PROJECT_ID=<your-project> DOMAIN=<your-domain> ./infra/gcp/deploy.sh roles

# 3. Build → migrate → deploy → smoke test
ENV=staging PROJECT_ID=<your-project> DOMAIN=<your-domain> ./infra/gcp/deploy.sh
```

4. **Cloudflare**: copy `infra/cloudflare/wrangler.toml.example` to `wrangler.toml`, put in your domain and the two `run.app` URLs that `deploy.sh` printed, then
   `npx wrangler deploy` and `npx wrangler secret put EDGE_SECRET` (value: `gcloud secrets versions access latest --secret=edge-shared-secret`).
   DNS: proxied (orange-cloud) records for `@`, `*` and `api` — any target, the Worker answers. SSL mode **Full (strict)**.
5. **Budget alerts**: Billing → Budgets → $50 / $80 / $100 per month.
6. **GitHub**: add the repository variables `bootstrap.sh` printed, plus `DOMAIN`. From then on, every push to `main` that passes CI deploys staging. Production: Actions → Deploy → Run workflow → production (add required reviewers to the `production` environment first).

## Every release

Push to `main` → CI → Deploy (staging). Or by hand: `ENV=staging ./infra/gcp/deploy.sh`.
Steps: `build` (Cloud Build) → `migrate` (job) → `deploy` (API, then web) → `smoke`.
Run one step with `./infra/gcp/deploy.sh <step>`; deploy an existing image with `TAG=<tag>`.

**Rollback**: Cloud Run → service → Revisions → route 100% to the previous revision (seconds). Migrations only ever add (expand/contract, docs/10 §5), so the old code keeps working.

## Public website only, on Vercel (before the API is deployed)

The bare-domain website (home page, privacy, terms) can run on its own on Vercel. School sign-in is
hidden and every other page redirects to the home page.

1. vercel.com → **Add New → Project** → import `manashsingh52/School_ERP`.
2. **Root Directory**: `apps/web`. Vercel reads `apps/web/vercel.json` (install from the repo root, build
   with Turborepo so the shared packages are built first). Leave the other build settings as detected.
3. **Environment variable**: `SITE_ONLY` = `true`. Nothing else is needed.
4. **Deploy**. Later, add your domain under Project → Settings → Domains.

### Or: the whole product as a live demo on Vercel

Set `DEMO_MODE` = `true` instead of `SITE_ONLY`. The site then also serves the school portal and the
owner console with the sample school recorded in `apps/web/demo/fixtures.json`: visitors pick a role
(school admin, teacher, parent, Bastaa owner) at `/login`, browse every screen, and any change is
politely refused. Dates move with the calendar, so "today" is always today. No API or database is
needed. After UI changes, record it again (`apps/web/tool/demo/record.mjs` explains how).

When the API is live (steps above), remove `SITE_ONLY` or `DEMO_MODE`, set `API_URL`, `APP_BASE_DOMAIN` and
`BFF_SHARED_SECRET`, and add a wildcard domain (`*.bastaa.in`) for school subdomains, or keep the web
on Cloud Run as scripted.

## Production needs first (SETUP-LATER)

Production uses real providers only (the API refuses the sandbox ones there):

- SMS (optional; needs DLT registration, SETUP-LATER #4): secrets `msg91-auth-key` plus `msg91-otp-template-id` (sign-in codes) and/or `msg91-sms-template-id` (notifications). Without them production runs with passwords and codes from the school office.
- Razorpay: each school connects its own keys in Settings (no platform secret)
- Optional: `gemini-api-key` (AI assistant, #19), `resend-api-key` (email, #9)

Add a secret: `printf '%s' "<value>" | gcloud secrets create <name> --data-file=-`, then grant the API's service account `roles/secretmanager.secretAccessor` on it.

## Notes

- **Row-level security on Cloud SQL**: managed Postgres can't grant `BYPASSRLS`, so the platform role reads all rows through its own `platform_all` policies (`apps/api/scripts/apply-sql.mjs`). Local development and tests use the same setup.
- **Same image to production** (docs/10 §5): production currently builds from the same commit in its own project. Promoting the exact staging digest needs a shared Artifact Registry — worth doing once production has paying schools.
- Upgrade path to the full topology (docs/10 §2): Google load balancer instead of the Worker, a separate `worker` service (`RUN_WORKERS=true` on its own, API with `RUN_WORKERS=false`), private IP for Cloud SQL.
